## 零、配置层

### 0.1 层级职责

配置层负责项目所有配置的统一管理，包括资源配置和业务配置的分离管理。

**核心职责**：

- 资源配置管理：管理Neo4j、VLLM、Milvus等资源的配置
- 业务配置管理：管理各业务的配置，包括业务所需的资源配置引用
- 配置加载与验证：系统启动时加载、验证所有配置
- 配置热更新：支持配置的热更新（可选）

**配置分类**：

1. **资源配置**：定义资源的连接参数、池化参数等
2. **业务配置**：定义业务的参数、所需的资源配置引用

### 0.3 资源配置规范

每个资源配置文件包含资源配置类和资源池配置：

```python
# src/config/resources/neo4j_config.py
class Neo4jResourceConfig(BaseResourceConfig):
    """Neo4j资源配置"""
    config_id: str = "neo4j_config"  # 配置文件名作为唯一标识
    uri: str = "neo4j+s://..."
    user: str = "..."
    password: str = "..."
    database: str = "neo4j"

# 资源池配置
neo4j_pool_config = PoolConfig(
    max_size=10,
    min_idle=2,
    idle_timeout=300000,
    max_wait_time=5000
)
```

### 0.4 业务配置规范

每个业务配置文件包含业务参数和所需的资源配置引用：

```python
# src/config/business/consult_service_config.py
class ConsultServiceConfig(BusinessConfig):
    """健康咨询业务配置"""
    business_id: str = "consult_service"
    
    # 所需的资源配置文件名列表（不含.py后缀）
    resource_configs: List[str] = ["neo4j_config", "vllm_config"]
    
    # 业务参数
    max_retries: int = 3
    timeout: int = 30
```

### 0.5 配置加载流程

系统启动时按以下顺序加载配置：

1. **扫描业务配置目录** → 发现所有业务配置文件
2. **解析业务配置** → 收集所需的资源配置文件名
3. **资源配置去重** → 多个业务引用同一资源配置时只加载一次
4. **加载资源配置** → 加载所需的资源配置
5. **创建资源池** → 根据资源配置创建对应的ResourcePool

### 0.6 资源共享机制

当多个业务配置引用同一资源配置时：

- **只创建一个ResourcePool实例**
- **所有业务共享该ResourcePool**
- **业务关闭不影响共享的ResourcePool**
- **系统关闭时销毁所有ResourcePool**





## 一、接入层

### 1.1 层级职责

接入层是系统对外暴露的唯一入口，负责HTTP协议处理、请求参数校验、SSE流式响应管理。

**核心职责**：

- 对外提供RESTful API接口，接收总项目后端的请求
- 处理SSE流式响应，实现内容的逐块返回
- 请求参数合法性校验、异常统一处理
- 协议转换，将外部请求转换为内部上下文格式

**上下游交互**：

- **上游**：对接总项目后端服务，接收健康咨询和报告生成请求
- **下游**：调用服务层的业务处理入口，传递请求上下文
- **响应**：将服务层返回的结果返回给上游调用方

## 二、服务层

### 2.1 层级职责

服务层位于接入层之下、编排层之上，负责业务逻辑的初步封装，是组合编排层中各种策略或资源的地方。

**核心职责**：

- 接收Controller传递的请求参数，构建内部上下文对象
- 执行初步的业务逻辑判断和参数预处理
- 组合、使用编排层的策略与资源，驱动完整的业务流程
- 管理请求生命周期内的状态和资源

**上下游交互**：

- **上游**：接收接入层传递的已校验请求
- **下游**：组合编排层的业务策略与agent容器类，执行编排agent任务
- **返回**：将编排层返回的结果透传回接入层

## 三、编排层

### 3.1 层级职责

编排层是系统的**核心大脑**，负责整个业务流程的状态机驱动和Agent策略执行。

**核心职责**：

- 实现基于有限状态机(FSM)的业务逻辑控制
- **封装业务策略**：针对不同业务场景（健康咨询/健康报告）特殊封装业务策略逻辑
- 驱动工具调用和内容生成，协调各阶段的输入输出
- 管理执行状态，控制流式生成节奏
- 使用MCP代理层的mcp代理工具

**上下游交互**：

- **上游**：接收服务层传递的请求上下文（包含完整对话记录或监测数据）
- **下游**：通过MCP代理层调用各种**真正的Tool**能力；通过**模型业务服务**使用AI模型等资源
- **回调**：将生成的内容块实时回调给服务层进行流式返回

**自动重新初始化机制**：

ToolCallHandler实现了自动重新初始化机制，确保即使release()被调用后，后续请求仍能正常工作：

1. `call_tool()`方法会检查工具是否已初始化
2. 如果未初始化，会自动调用`_ensure_initialized()`从MCPProxyFactory获取工具实例
3. MCPProxyFactory会缓存工具实例，避免重复创建
4. `release()`方法只是将当前handler对工具的引用设置为None，不会释放MCP代理工具实例

model_business_service包内有一个Impl包，Impl包里的类是专为agent或chain使用的模型调用类，每一个tool调用类都是为一个特定的业务所设计，并且使用MCP代理层所提供的tool服务。model_business_service包对外设置一个统一的ModelBusinessService接口，所有的tool调用类都必须实现ModelBusinessService接口。



## 四、MCP代理层

### 4.1 层级职责

MCP代理层（Model Context Protocol Agent Layer）在编排层和工具实现层之间提供统一的工具调用接口，屏蔽底层工具实现差异。

**核心职责**：

- 提供统一的工具调用接口，屏蔽底层工具实现差异
- 支持标准MCP协议（真MCP代理）和高效直连（伪MCP代理）两种调用方式
- 工具实例的生命周期管理、缓存
- 协议转换：将编排层的抽象调用转换为具体工具的执行请求

> ⭐ **重要**：MCP代理层只代理**真正的Tool**（如Neo4jMedicalTool、VectorEnhancedRetrievalTool、ValidationTool），不代理模型调用！模型调用由编排层的模型业务服务（orchestration/model_business_service包中）直接完成。

**上下游交互**：

- **上游**：接收编排核心层的工具调用请求
- **下游**：路由到工具实现层的对应工具执行具体逻辑
- **返回**：将工具执行结果返回给编排核心层

#### 5.2.3 Tool与资源管理层协作规范

**重要说明**：Tool层不应直接创建和管理连接，必须通过资源管理层获取资源。

**Tool资源获取规范**：

1. **禁止直接创建连接**：Tool不应直接创建和管理连接，应通过资源池获取资源
2. **资源获取方式**：Tool的`_init_resource()`方法应从GlobalResourceManager获取资源句柄
3. **资源释放方式**：Tool的`release_source()`方法应释放资源句柄归还资源池（不断开连接）
4. **资源销毁方式**：Tool的`destroy_source()`方法应彻底销毁资源（断开连接）

**Tool与资源管理层协作示例**：

```python
# 正确示例：Neo4j医疗知识图谱工具使用资源池
# tools/neo4j_medical_tool/neo4j_medical_tool.py
from src.resource_manager import GlobalResourceManager

class Neo4jMedicalTool(Tool):
    """
    Neo4j医疗知识图谱工具
    
    提供医疗知识图谱的查询能力
    使用资源池管理Neo4j连接
    """
    
    def __init__(self):
        self._resource_handle = None
        self._adapter = None
    
    def _init_resource(self):
        """初始化所用资源 - 从资源池获取连接"""
        # 从全局资源管理器获取Neo4j连接资源
        self._resource_handle = GlobalResourceManager.acquire("neo4j_connection")
        self._adapter = self._resource_handle.get_client().get_adapter()
    
    def release_source(self):
        """释放所用资源 - 归还资源池，保持连接"""
        if self._resource_handle:
            GlobalResourceManager.release(self._resource_handle)
            self._resource_handle = None
            self._adapter = None
    
    def destroy_source(self):
        """彻底销毁资源 - 断开连接"""
        if self._resource_handle:
            GlobalResourceManager.destroy(self._resource_handle)
            self._resource_handle = None
            self._adapter = None
    
    def query_medical_knowledge(self, query: str) -> List[Dict]:
        """查询医疗知识"""
        return self._adapter.execute_query(query)
```

**错误示例（禁止）**：

```python
# 错误示例：Tool直接创建和管理连接
class Neo4jMedicalTool(Tool):
    def __init__(self):
        # 错误：直接创建adapter，绕过资源池
        self._adapter = Neo4jAdapterImpl(uri="...", user="...", password="...")
        self._adapter.connect()
    
    def release_source(self):
        # 错误：直接断开连接，无法复用
        self._adapter.disconnect()
```

**新增方法**：

| 方法                                   | 说明                                         |

**acquire()方法重构流程**：

```
1. 加锁
2. 检查空闲池 → 有空闲资源？
   ├─ YES → 直接分配，返回ResourceHandle
   └─ NO  → 继续
3. 检查动态创建 → allow_dynamic_creation == True？
   ├─ YES → 检查容量 → total < max_size？
   │       ├─ YES → 创建前检查 → 通过？
   │       │       ├─ YES → 创建新资源，分配，返回
   │       │       └─ NO  → 进入等待队列
   │       └─ NO  → 进入等待队列
   └─ NO  → 进入等待队列
4. 进入等待队列 → 队列未满？
   ├─ YES → 创建ResourceRequest，加入队列，释放锁，等待Event
   │       ├─ 收到通知 → 返回分配的资源
   │       └─ 超时 → 从队列移除，返回None
   └─ NO  → 返回None（拒绝服务）
```

**release()方法增强**：

```
1. 加锁
2. 归还资源到空闲池
3. 检查等待队列 → 队列非空？
   ├─ YES → 取出队首请求 → 分配资源 → event.set()通知
   └─ NO  → 结束
4. 释放锁
```



#### 6.2.5 线程安全保证机制

**锁的使用范围**：
- `_lock`保护以下共享状态：
  - `_idle_resources`：空闲资源字典
  - `_active_resources`：活跃资源字典
  - `_pending_requests`：等待队列

**Event通知机制**：
- `ResourceRequest.event`用于阻塞等待资源分配
- `event.set()`触发通知，唤醒等待线程
- `event.wait(timeout)`阻塞等待，支持超时

**队列操作原子性**：
- 入队、出队操作在锁保护下进行
- 超时请求清理在锁保护下进行



#### 6.2.6 排队算法设计

**FIFO顺序保证**：
- 使用`collections.deque`作为等待队列
- 新请求从右端入队（`append`）
- 分配时从左端出队（`popleft`）

**队列容量限制**：
- 队列大小由`max_pending_requests`配置
- 队列满时新请求直接返回None



#### 6.2.7 原架构兼容方案

**默认配置兼容**：
- 新增配置项都有默认值
- 不指定新配置项时，行为与原有实现一致

**API兼容**：
- `acquire(wait_ms)`方法签名不变
- `release(handle)`方法签名不变
- 调用方代码无需修改



#### 6.2.8 资源创建防崩溃机制

资源创建过程中，尤其是模型资源的创建，可能因系统内存或显存不足导致严重后果：

| 崩溃场景 | 原因 | 后果 |
|----------|------|------|
| 操作系统崩溃 | 物理内存耗尽触发OOM Killer | 系统强制杀死进程，所有服务中断 |
| 项目系统崩溃 | 进程内存超限被系统终止 | 项目所有业务中断，已创建资源丢失 |
| 已创建资源崩溃 | 显存不足导致CUDA错误 | 已加载的模型推理失败，GPU资源不可用 |

系统设计三层防护机制，从预防、隔离、验证三个维度确保资源创建的安全性：

```
┌─────────────────────────────────────────────────────────────┐
│               资源创建三层防崩溃机制                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  第一层：创建前资源预检（预防）                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ ResourceCreationGuard.check_before_creation()       │   │
│  │   ├─ 检查可用内存（含20%安全余量）                    │   │
│  │   ├─ 检查可用显存（含20%安全余量）                    │   │
│  │   └─ 不通过 → 拒绝创建，请求进入等待队列              │   │
│  └─────────────────────────────────────────────────────┘   │
│                          ↓ 通过                              │
│  第二层：创建过程异常捕获与隔离（隔离）                       │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ _try_create_resource()                              │   │
│  │   ├─ MemoryError → 清理 + 返回None                  │   │
│  │   ├─ RuntimeError(CUDA) → 清理GPU缓存 + 返回None    │   │
│  │   ├─ 其他Exception → 清理 + 返回None                │   │
│  │   └─ 异常不得向上抛出，不得影响_active_resources      │   │
│  └─────────────────────────────────────────────────────┘   │
│                          ↓ 创建成功                          │
│  第三层：创建后资源验证（验证）                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ _validate_created_resource()                        │   │
│  │   ├─ 基础验证：资源对象非空且属性完整                  │   │
│  │   ├─ 连通性验证：资源可正常连接/调用                   │   │
│  │   └─ 验证失败 → 清理失败资源 + 返回None              │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**第一层：创建前资源预检**

由`ResourceCreationGuard`负责，在资源创建前检查系统可用资源是否满足需求：

- 检查可用内存是否 ≥ `min_memory_mb` × 1.2（含20%安全余量）
- 检查可用显存是否 ≥ `min_vram_mb` × 1.2（含20%安全余量）
- 安全余量原因：模型加载过程中会产生临时数据结构，CUDA运行时也需要额外显存
- 预检不通过时，拒绝创建，请求进入等待队列

**第二层：创建过程异常捕获与隔离**

由`ResourcePool._try_create_resource()`负责，确保创建过程中的任何异常不会影响系统稳定性：

- 所有异常在`_try_create_resource`内部捕获，**不得向上抛出**
- `MemoryError`：内存不足，清理后返回None
- `RuntimeError(CUDA)`：CUDA错误，清理GPU缓存后返回None
- 其他`Exception`：未知异常，清理后返回None
- 创建失败**不得修改**`_active_resources`中的任何已有资源

**第三层：创建后资源验证**

由`ResourcePool._validate_created_resource()`负责，确保创建的资源真正可用：

- 基础验证：资源对象非空且属性完整（`resource.is_valid()`）
- 连通性验证：资源可正常连接/调用（`resource.health_check()`）
- 验证失败时调用`_cleanup_failed_resource()`清理失败资源

**防崩溃相关配置项与资源类型对应关系**：

| 资源类型 | pre_create_check_enabled | min_memory_mb | min_vram_mb | 说明 |
|----------|--------------------------|---------------|-------------|------|
| 数据库连接 | False | 256 | 0 | 连接创建成本低，无需检查显存 |
| 向量模型 | True | 1024 | 2048 | 需要检查显存，防止OOM |
| LLM模型 | True | 4096 | 8192 | 必须检查显存，防止系统崩溃 |
| Embedding模型 | True | 512 | 1024 | 需要检查显存 |

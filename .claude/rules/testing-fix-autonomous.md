# 无监督测试修复规范

> **与 ECC 关系**：补充。ECC `common/testing.md` 覆盖通用 TDD/覆盖率/AAA 模式，本规则补充项目特有的无监督（全自动）测试修复约束。

## 规则定位

本规范适用于**除特殊情况外AI全自主的测试修复闭环**：AI 反复执行测试和修复，直到测试无问题或达标测试计划才退出，或遇到特殊情况暂停。用户只关注最终结果，过程中无需介入。

与 `testing-supervised.md`（用户监督测试规范）的区别：

| 维度 | 用户监督 | 无监督（本规范） |
|------|---------|-----------------|
| 执行方式 | 阶段性完成，汇报后等用户审核批准 | AI 完全自主，循环到结束 |
| 阶段推进 | 用户审核通过后才进入下一阶段 | AI 自行推进 |
| 设计缺陷 | 汇报时一并提出，用户裁决 | 暂停并汇报用户 |
| 修复审批 | 修复完成后汇报，用户审核 | 实现缺陷自动修复，无需审批 |
| 用户角色 | 审核者，逐阶段把关 | 仅接收最终汇报 |
| 循环终止 | 用户审核不通过或全部通过 | 全部通过或设计缺陷暂停 |

## 触发方式

通过 `/loop` 指令启动持续测试-修复循环，或由用户直接指示"全自动测试修复"。

## 自主执行原则

1. **全自动决策** — 实现缺陷的修复方案由 AI 自主判断，无需用户确认
2. **最小修复** — 仍遵循 `post-test-fix.md` 的最小修复原则，不扩大修复范围
3. **证据驱动** — 每个修复判断必须有测试输出、日志、调用链或设计文档依据
4. **设计边界** — 涉及设计变更时必须暂停，不擅自修改设计
5. **自动回归** — 每次修复后自动执行回归验证，不等待用户指令

## 测试总则

### 架构测试与业务测试

与 `testing-supervised.md` 一致：**必须先架构测试再业务测试**。

### 架构测试检查项

| 检查项 | 说明 | 相关 Rule |
|--------|------|-----------|
| 七层依赖方向 | 是否存在反向依赖或跨层调用 | `architecture.md` |
| 适配层使用 | 外部依赖是否通过适配层访问 | `architecture.md` |
| 资源管理合规 | 资源是否通过 GlobalResourceManager 获取 | `resource-management.md` |
| 命名规范 | 类名/方法名/变量名/包名/文件名 | `naming.md` |
| 层间交互 | 相邻层是否通过接口交互 | `architecture.md` |

### 业务测试检查项

| 检查项 | 说明 |
|--------|------|
| 功能逻辑 | 业务功能是否按设计文档预期工作 |
| API 接口行为 | 请求参数校验、响应格式、状态码 |
| 数据流完整性 | 数据从接入层到适配层的完整流转 |
| 异常处理 | 异常场景是否正确处理和返回 |
| 资源释放 | 资源是否正确释放，无泄漏 |

## 测试类型要求

三种测试类型全部必需：

1. **单元测试** — 单个函数、方法的正确性
2. **集成测试** — 层间交互、资源池访问、适配层调用
3. **E2E 测试** — 关键用户流程（健康咨询、报告生成）

## 测试环境

必须使用 MedicalQA conda 环境：

```bash
conda activate MedicalQA
pytest
```

## 自主闭环流程

```
测试验收 → 记录全部问题 → 按严重级别排序 → 逐项分类根因
→ 实现缺陷：自动修复 → 回归验证 → 下一项
→ 设计缺陷：暂停循环，汇报用户 → 等待裁决
→ 环境问题：暂停循环，汇报用户 → 等待确认
→ 全部通过：输出最终报告，结束循环
```

### 修复优先级

按严重级别从高到低修复：

1. CRITICAL — 必须修复，否则阻塞后续测试
2. HIGH — 必须修复
3. MEDIUM — 尽量修复
4. LOW — 记录，本轮可选修复

### 每轮修复后的自动操作

1. `codegraph sync` — 更新代码图索引
2. 回归测试 — 先验证原失败点，再验证受影响范围
3. 代码审查 — 调用 ECC python-reviewer / fastapi-reviewer
4. 更新测试记录 — 标记修复状态
5. **更新 memory** — 更新已修复问题的状态，补充修复方式；删除已验证通过的临时记录

### memory 管理

无监督测试修复是反复迭代过程，**必须严格管理 memory 的更新和清理**，防止过期或错误信息导致后续判断失误：

- **修复后立即更新** — 将对应问题状态更新为"已修复"，补充修复方式和验证结果
- **重新测试后覆盖** — 新一轮测试发现与旧 memory 不一致时，以最新结果覆盖旧记录
- **已关闭问题清理** — 问题已修复且回归通过后，删除对应测试记录，只保留未解决问题
- **整轮通过后清理** — 全部测试通过时，清理本轮所有测试 memory，只保留最终报告摘要
- **禁止堆积** — 不得保留已过时的中间状态记录（如"修复中"、"待验证"等已不反映当前状态的条目）

### 循环终止条件

| 条件 | 行为 |
|------|------|
| 全部测试通过 | 输出最终报告，循环结束 |
| 遇到设计缺陷 | 暂停循环，汇报用户，等待裁决 |
| 遇到环境问题 | 暂停循环，汇报用户，等待确认 |
| 同一问题修复 3 次仍失败 | 暂停循环，汇报用户，说明失败原因 |
| 用户主动叫停 | 立即停止，输出当前进度报告 |

## 遇到设计缺陷或环境问题等特殊问题时

与 `testing-supervised.md` 一致，**必须暂停并向用户汇报**：

1. 设计缺陷 — 设计文档有错误或不合理之处
2. 设计冲突 — 多份设计文档之间存在矛盾
3. 设计缺失 — 实现需要但设计文档未覆盖的场景
4. 可改进设计 — 有明确优化建议但不属于缺陷
5. 环境问题 — 环境配置、资源状态、硬件条件等不满足要求，修改可能影响系统运行
6. 其他特殊情况 — AI 无法自主判断或超出自动执行范围的情形

汇报格式：
- 测试现象和复现步骤
- 定位证据（调用链、日志、代码位置）
- 可选方案及其利弊
- 建议方案

用户裁决或确认后方可继续修复。

## 最终报告

循环结束时，输出结构化报告：

1. 测试总轮次和耗时
2. 发现问题总数（按严重级别分类）
3. 已修复问题列表（含修复方式）
4. 未修复问题列表（含原因）
5. 需要用户裁决的设计问题
6. 当前测试覆盖率
7. 遗留风险和建议

## 日志审视规范

与 `testing-supervised.md` 一致：

1. **本该输出但未输出的日志，直接视为该功能执行失败**
2. **不能放过任何 warning 或 error**
3. 所有发现必须记录，不可遗漏

## 覆盖率要求

最低测试覆盖率：**80%**

## 测试工具

- **框架**：pytest
- **架构测试辅助**：codegraph
- **API 测试**：FastAPI TestClient
- **代码审查**：ECC python-reviewer / fastapi-reviewer / security-reviewer

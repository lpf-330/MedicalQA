# 用户监督测试规范

> **与 ECC 关系**：补充。ECC `common/testing.md` 覆盖通用 TDD/覆盖率/AAA 模式，本规则补充项目特有的用户监督测试约束。

## 规则定位

本规范适用于**用户监督下的测试-修复闭环**：AI 按阶段完成工作并汇报，用户审核汇报内容后决定是否进入下一阶段。测试与修复严格分阶段执行。

与 `testing-fix-autonomous.md`（无监督测试修复规范）的区别：

| 维度 | 用户监督（本规范） | 无监督 |
|------|-------------------|--------|
| 执行方式 | 阶段性完成，汇报后等用户审核批准 | AI 完全自主，循环到结束 |
| 阶段推进 | 用户审核通过后才进入下一阶段 | AI 自行推进 |
| 设计缺陷 | 汇报时一并提出，用户裁决 | 暂停并汇报用户 |
| 修复审批 | 修复完成后汇报，用户审核 | 实现缺陷自动修复，无需审批 |
| 用户角色 | 审核者，逐阶段把关 | 仅接收最终汇报 |

## 阶段划分

测试-修复闭环按以下阶段推进，每阶段完成后必须汇报用户，用户审核通过后才进入下一阶段：

| 阶段序号 | 阶段名称 | 工作内容 | 阶段产出 |
|----------|---------|---------|---------|
| 1 | 架构测试 | 白盒审查七层依赖、适配层、资源管理、命名、层间交互 | 架构测试报告（问题清单） |
| 2 | 架构问题修复 | 按 `post-test-fix.md` 修复架构问题，回归验证 | 修复记录和验证结果 |
| 3 | 业务测试 | 白盒+黑盒+生产模拟 | 业务测试报告（问题清单） |
| 4 | 业务问题修复 | 按 `post-test-fix.md` 修复业务问题，回归验证 | 修复记录和验证结果 |
| 5 | 最终回归 | 全量回归验证 | 最终测试报告 |

用户可在任意阶段审核时提出修改意见或额外要求。

### 阶段汇报格式

每阶段汇报必须包含：

1. 本阶段执行内容摘要
2. 发现的问题清单（编号、严重级别、描述、影响范围）
3. 修复内容（如适用，含修复方式和验证结果）
4. 需要用户裁决的设计问题（如有）
5. 下一阶段计划
6. 等待用户审核批准

### 遇到设计缺陷时

在汇报中单独列出，由用户裁决。不擅自修复或绕过设计问题。

## 测试总则

### 架构测试与业务测试

测试分为两个阶段，**必须先架构测试再业务测试**：

| 阶段 | 测试重点 | 说明 |
|------|----------|------|
| 架构测试 | 代码结构合规性 | 验证代码是否遵循七层架构规范 |
| 业务测试 | 功能逻辑正确性 | 验证业务功能是否按预期工作 |

**为什么先架构后业务**：架构违规会导致后续所有业务测试的基础不成立，必须先确保架构正确。

### 架构测试检查项

| 检查项 | 说明 | 相关 Rule |
|--------|------|-----------|
| 七层依赖方向 | 是否存在反向依赖或跨层调用 | `architecture.md` |
| 适配层使用 | 外部依赖是否通过适配层访问 | `architecture.md` |
| 资源管理合规 | 资源是否通过 GlobalResourceManager 获取 | `resource-management.md` |
| 命名规范 | 类名/方法名/变量名/包名/文件名 | `naming.md` |
| 层间交互 | 相邻层是否通过接口交互 | `architecture.md` |

### 业务测试检查项

| 检查项 | 说明 |
|--------|------|
| 功能逻辑 | 业务功能是否按设计文档预期工作 |
| API 接口行为 | 请求参数校验、响应格式、状态码 |
| 数据流完整性 | 数据从接入层到适配层的完整流转 |
| 异常处理 | 异常场景是否正确处理和返回 |
| 资源释放 | 资源是否正确释放，无泄漏 |

## 测试类型要求

三种测试类型全部必需：

1. **单元测试** — 单个函数、方法的正确性
2. **集成测试** — 层间交互、资源池访问、适配层调用
3. **E2E 测试** — 关键用户流程（健康咨询、报告生成）

## 测试环境

必须使用 MedicalQA conda 环境：

```bash
conda activate MedicalQA
pytest
```

## 测试-修复闭环

### 两阶段分离

测试与修复严格分为两个阶段：

| 阶段 | 行为 | 规则 |
|------|------|------|
| 测试阶段 | 只记录问题，不修复问题 | 确保测试客观性 |
| 修复阶段 | 按 `post-test-fix.md` 修复 | 修复完成汇报用户审核 |

**测试阶段只记录不修复**，确保测试发现的完整性不被修复行为干扰。

## 日志审视规范

测试过程中必须采用严格审视态度：

1. **本该输出但未输出的日志，直接视为该功能执行失败**
2. **不能放过任何 warning 或 error**
3. 所有发现必须记录，不可遗漏

## 覆盖率要求

最低测试覆盖率：**80%**

## 测试工具

- **框架**：pytest
- **架构测试辅助**：codegraph（codegraph_callers/codegraph_callees/codegraph_impact 分析依赖关系）

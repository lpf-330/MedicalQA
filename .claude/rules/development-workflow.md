# 业务开发流程规范

> **与 ECC 关系**：覆盖。ECC 全局 `common/development-workflow.md` 定义了通用开发流程（研究→规划→TDD→审查→提交），本规则覆盖为项目特有的业务开发流程，补充架构依托、codegraph 实时更新等约束。

## 业务开发设计依据

规划业务开发任务和实施业务功能开发时，**必须根据**当前最新的相关设计文档，包括但不限于：

1. 最新的项目架构原则与使用规范文档（`doc/项目设计文档/项目架构设计/`）
2. 最新的项目架构设计文档（`doc/项目设计文档/项目架构设计/`）
3. 最新的项目业务详细设计文档（`doc/项目设计文档/项目详细设计/`）
4. 最新的数据库设计文档（`doc/项目设计文档/数据库设计/`）
5. 与当前开发任务相关的其他最新设计文档

开发时必须忠实按照最新相关设计文档中的设计实现，确保业务功能符合当前设计约束。

## 禁止擅自修改设计

在开发业务功能时，**不能擅自修改当前最新设计文档中的任何设计**，包括但不限于项目架构、业务流程、接口契约、数据结构、数据库设计、资源管理机制和层间交互方式。只能在既有设计约束内实现业务功能逻辑。

如果在开发中遇到设计缺陷、可改进设计、设计冲突、设计缺失、相关疑问或实现问题，必须向开发者咨询并说明情况，由开发者裁决合适方案后再继续实施。

如开发者明确授权修改架构，架构修改规范见 `architecture.md`。

## codegraph 实时更新规范

**每个类/接口的增删改后，必须立即执行 `codegraph sync` 更新索引。**

目的：确保后续类开发时基于最新的代码图索引，避免使用已修改或已删除的类/接口。

## 新业务功能开发流程

### 步骤概览

1. **阅读设计文档** — 最新的项目架构设计文档和架构原则与使用规范文档
2. **分析现有代码** — 使用 codegraph（context/callers/callees）分析依赖和调用链
3. **检查适配层** — `codegraph search adapter`，外部依赖是否已有适配
4. **逐层开发** — 按层级自上而下（Controller → Service → 编排 → MCP → Tool → 资源管理 → 适配）
5. **每个类完成后** — 立即 `codegraph sync` 更新索引
6. **架构测试** — 验证七层依赖、适配层使用、资源管理合规（详见 `testing-supervised.md`）
7. **业务测试** — 验证功能逻辑、API 接口、数据流（详见 `testing-supervised.md`）
8. **代码审查** — 调用 ECC python-reviewer / fastapi-reviewer

### 开发顺序

按层级自上而下开发：

```
Controller → Service → Agent/Chain策略 → ToolCallHandler(可选) → MCP代理(可选) → Tool(可选) → 资源封装(可选) → 适配层(可选)
```

每层开发完成后，再进入下一层。不在同一时间内跨多层开发。

## 开发最佳实践

1. **依赖注入** — 使用构造函数注入依赖，不在类内部创建依赖
2. **资源管理** — 使用上下文管理器（with语句）自动管理资源
3. **异常处理** — 统一异常处理，记录日志
4. **类型注解** — 所有公共方法添加类型注解
5. **接口定义** — 使用 abc 模块定义接口
6. **数据类定义** — 使用 dataclass 定义数据类

# 测试后修复规范

> **与 ECC 关系**：补充。ECC 全局 rules 覆盖通用 TDD、代码审查、安全和错误处理要求，本规则补充项目测试验收之后的问题修复流程。

## 规则继承

本规则继承 `development-workflow.md` 中关于最新设计文档、禁止擅自修改设计、遇到设计问题必须咨询开发者的约束。

测试后修复时，必须忠实按照当前最新相关设计文档中的设计进行修复；不得为了让测试通过而擅自修改业务流程、接口契约、数据结构、数据库设计、资源管理机制、层间交互方式或其他设计约束。

如果根因指向设计缺陷、设计冲突、设计缺失、可改进设计或设计疑问，必须向开发者说明测试现象、定位证据和可选方案，由开发者裁决后再继续修复。

## 自动执行规则

修复过程全自动执行，无需用户逐步审批：

1. **实现缺陷** — AI 自主判断修复方案，直接修改代码，无需确认
2. **测试缺陷** — AI 自主修正测试与设计不一致之处，无需确认
3. **设计缺陷** — **必须暂停**，汇报用户，等待裁决后方可继续
4. **环境问题** — **必须暂停**，汇报用户，环境修改可能影响系统运行和其他服务，须用户确认后方可继续
5. **数据问题** — AI 自主处理，无需确认；涉及生产数据时暂停汇报

### 重试上限

同一问题连续修复 3 次仍失败时，**必须暂停并汇报用户**，说明：
- 已尝试的修复方案和每次的结果
- 失败的可能原因
- 建议的下一步方案

## 适用范围

本规则适用于测试验收、架构测试、业务测试、日志分析、手工验证或回归测试之后的问题修复。

不适用于纯测试验收工作。测试验收必须遵循 `testing-supervised.md`（用户监督）或 `testing-fix-autonomous.md`（无监督）：只记录问题，不修复问题。

## 修复输入要求

开始修复前，必须先确认问题来源：

1. 测试记录、失败用例、日志片段或复现步骤
2. 期望行为及其依据的最新设计文档位置
3. 实际行为、影响范围和严重级别
4. 是否存在 warning、error 或本应输出但缺失的日志

信息不足时，先向开发者询问，不得凭猜测扩大修复范围。

## 修复流程

1. **读取测试记录** — 明确失败现象、复现方式、期望行为和影响范围
2. **核对设计依据** — 查阅当前最新相关设计文档，确认正确行为
3. **复现问题** — 使用相同测试、最小复现步骤或相关日志确认问题存在
4. **定位根因** — 使用 codegraph（context/callers/callees/impact）分析调用链和影响范围
5. **判断设计边界** — 区分实现缺陷、测试缺陷和设计问题
6. **最小修复** — 只修改导致失败的必要代码，不顺手重构或扩展功能
7. **实时更新索引** — 每个类/接口增删改后立即执行 `codegraph sync`
8. **回归验证** — 先运行失败相关测试，再按影响范围运行架构测试和业务测试
9. **代码审查** — 修改代码后调用 ECC python-reviewer / fastapi-reviewer，涉及安全、数据库、外部 API 或文件系统时追加 security-reviewer
10. **记录结果** — 说明修复点、验证结果、未解决风险和需要开发者裁决的问题

## 修复顺序

测试后修复按证据链推进，不按业务开发的自上而下逐层开发顺序推进：

```
测试现象 → 设计依据 → 复现确认 → 调用链定位 → 根因分类 → 最小代码修复 → 回归验证 → 代码审查
```

如果根因跨多个层级，优先修复最靠近根因的一层；不得为了绕过问题在上层添加兼容、兜底或特殊分支。

## 根因分类

| 类型 | 处理方式 |
|------|----------|
| 实现缺陷 | 按最新设计文档做最小修复 |
| 测试缺陷 | 说明测试与设计不一致之处，向开发者确认后再修改测试 |
| 设计缺陷 | 暂停修复，提交证据和方案给开发者裁决 |
| 环境问题 | 暂停修复，汇报环境差异和修改方案，等待用户确认 |
| 数据问题 | 按数据库设计文档和数据来源确认，不擅自修改数据库设计或生产数据 |

## 最佳实践

1. **证据优先** — 每个修复判断都应对应测试输出、日志、调用链或设计文档依据
2. **最小变更** — 只修复当前测试暴露的问题，不混入重构、风格调整或新功能
3. **先确认后修改测试** — 测试与实现冲突时，先确认设计依据，不默认测试错误
4. **保留架构边界** — 不跨层调用，不绕过 MCP、Tool、ResourceManager 或 Adapter 约束
5. **资源合规** — 涉及数据库、模型或外部依赖时，仍必须通过 GlobalResourceManager 和适配层
6. **异常显式处理** — 不得静默吞掉异常或用宽泛 fallback 掩盖失败
7. **日志严格审视** — warning、error 和缺失日志都必须纳入修复判断
8. **回归由近到远** — 先验证原失败点，再验证受影响调用链，最后按需要做完整回归
